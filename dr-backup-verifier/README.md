# DR Backup Verifier

**Бэкап, который ни разу не восстанавливали, — это не бэкап.** Инструмент не просто снимает дамп,
а доказывает, что из него можно поднять рабочую базу:

```
дамп источника ─► SHA-256 + манифест ─► изолированный временный контейнер ─► restore
      ─► сверка схемы и числа строк ─► проверки целостности ─► ваши SQL-проверки ─► УДАЛЕНИЕ теста ─► отчёт
```

Зависимостей нет: только Python ≥ 3.11 (stdlib) и Docker.

## Быстрый старт

```bash
make test        # 24 юнит-теста, Docker не нужен
make demo        # полный сценарий на демо-БД (нужен Docker)

cp config.example.toml config.toml   # настроить под себя
python3 -m verifier -c config.toml run
```

## Команды

| Команда | Что делает |
|---|---|
| `run` | бэкап → проверка → ротация (основной режим для cron) |
| `backup` | только снять бэкап |
| `verify [--backup FILE\|latest]` | проверить существующий бэкап |
| `list` | бэкапы и результат последней проверки |
| `cleanup` | удалить «осиротевшие» контейнеры и сети (метка `dr-verifier=1`) |

Флаги: `--keep-on-failure` (оставить контейнер для разбора), `--skip-checksum` (демо: пусть битый файл ловит restore).
Коды выхода: `0` — всё хорошо, `1` — бэкап не прошёл проверку, `2` — ошибка запуска/конфига.

## Что проверяется

1. **Целостность файла** — размер и SHA-256 против манифеста.
2. **RPO** (опц.) — возраст бэкапа ≤ `rpo_target_hours`.
3. **Изоляция** — временная сеть `--internal` (нет выхода наружу), порты не публикуются, лимиты памяти/CPU/процессов, одноразовый случайный пароль.
4. **Читаемость архива** — `pg_restore --list` / gzip-поток.
5. **Восстановление** — код возврата + замер времени = **измеренный RTO** (`rto_target_sec` опц.).
6. **Схема** — отпечаток всех колонок и типов совпадает с источником (сортировка в Python, поэтому не зависит от collation).
7. **Данные** — число строк в каждой таблице совпадает с манифестом (допуск настраивается).
8. **Целостность движка** — PostgreSQL: нет невалидных индексов; полное чтение всех данных (`pg_dump → /dev/null`). MySQL: `mysqlcheck`.
9. **Ваши бизнес-проверки** — произвольный SQL с `expect_equals / expect_min / expect_max`.
10. **Уборка** — контейнер, сеть и тома удаляются в `finally` (даже при ошибке, Ctrl+C и SIGTERM), затем проверяется, что их действительно нет.

Результат — текст в консоли и JSON в `reports/` (+ `latest.json`), уведомление в webhook/Telegram при провале.

## Автозапуск (cron)

```cron
0 3 * * *  cd /opt/dr-backup-verifier && SOURCE_DB_PASSWORD=... python3 -m verifier -c config.toml run >> /var/log/dr-verify.log 2>&1
```
Код выхода ≠ 0 удобно ловить мониторингом (Healthchecks, Zabbix, systemd `OnFailure=`).

## Структура

```
verifier/
  cli.py       команды и коды выхода        verify.py   ядро: пайплайн проверки
  backup.py    дамп, манифест, ротация      drivers.py  PostgreSQL / MySQL
  docker.py    обёртка над docker CLI       db.py       запросы и отпечаток БД
  runner.py    запуск процессов (gz-потоки) notify.py   webhook / Telegram
  config.py    TOML-конфиг                  report.py   отчёт текст/JSON
tests/         эмулятор Docker + тесты      demo/       демо-БД и конфиг
```

## Важные нюансы

- **Версия образа** (`verify.image`) должна совпадать с мажорной версией боевой СУБД, иначе вы проверяете не то.
- Если в источник активно пишут, число строк «в момент метаданных» и «в момент дампа» может чуть разойтись — используйте `row_count_tolerance_*`. Для тихих окон (ночь) оставьте 0.
- `use_tmpfs = true` кладёт данные теста в RAM; `memory` должна вмещать всю БД, иначе OOM.
- Бэкапы содержат боевые данные: храните `backup_dir` с правами 700 и шифруйте при выгрузке во внешнее хранилище (в проект не входит).
- Образ скачивается до старта изолированной сети; сам тестовый контейнер выхода в интернет не имеет.
- Добавить другую СУБД: реализуйте класс в `verifier/drivers.py` (команды dump/restore/query + критерий готовности).
